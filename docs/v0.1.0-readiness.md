# v0.1.0 readiness

**Date:** 2026-10-27  
**Branch:** `release/v0.1.0-readiness` (based on `main` at `c0d81b9`, merged as #5)  
**Scope:** P0 GitHub workbench, as described in the README and the research report.

## Verdict

**Good enough for v0.1.0 once this branch is merged.** The real TUI flow now loads the sidebar,
creates or reuses a worktree, creates a session, injects the PR context, and focuses the tab against
OpenCode 2.2.0 and a live GitHub repository. One real-host blocker was found and fixed here; without
that fix the sidebar never left "Loading GitHub…" in a real session, even though the full test suite
passed.

Publishing is not part of this branch. The package was `"private": true` here; the release checklist
below and [Releasing](#releasing) cover the remaining packaging steps.

## Published packaging defect

`0.1.0` published with provenance, but the registry tarball was not usable. `exports` pointed at
`.ts`/`.tsx` sources, and OpenCode applies its Solid transform to local sources but skips
`node_modules`. The installed TUI half therefore loaded as static JSX and never rendered the sidebar.
The local-directory E2E could not catch this because local sources do receive the transform.

`0.1.2` ships compiled ESM from `dist/`. `scripts/build.ts` builds with `@opentui/solid/bun-plugin`,
`pack:check` rejects an uncompiled TUI entrypoint, and the registry target must be re-run through the
TUI E2E before it is called good. The `0.1.2` publish workflow deprecates `0.1.0` once the new version
is verified on the registry.

`0.1.1` was tagged to ship this fix, but npm rejected its provenance entry with
`TLOG_CREATE_ENTRY_ERROR` (an equivalent transparency-log entry already existed), and no version was
published. `0.1.2` is the first release with the compiled package. Its first tag run hit the same
Rekor conflict; re-running the publish step in a fresh npm process signed a new entry and published.
The workflow now retries that specific error and checks the registry between attempts.

## Blocker found and fixed

**Symptom:** in a real session the GitHub sidebar rendered its header but stayed on
`Loading GitHub… /tmp/.../worktree/...` forever. The server RPCs worked when called directly.

**Root cause:** `src/tui/state.ts` imported `solid-js` from a `.ts` module. OpenCode 2.2.0 applies its
Solid transform (which rewrites `solid-js` to the host runtime) to `.tsx` sources; the `.ts` module
resolved the plugin's own `solid-js` server build instead. The two copies rendered, but signals
created in the host never reached effects created in `state.ts`. The location-change effect therefore
ran once with the initial project location, missed the session's worktree location, and never
recovered. An identity probe confirmed `state.ts` and `sidebar.tsx` were using different Solid module
namespaces.

**Fix:** renamed the module to `src/tui/state.tsx` (it still contains no JSX) and documented the
constraint in the module header. `test/tui-runtime.test.ts` now fails if a `.ts` source imports a host
runtime module (`solid-js`, `solid-js/store`, `@opentui/*`, or `@opencode/plugin/tui`) at runtime;
type-only imports remain allowed.

**Why the tests missed it:** `test/preload.ts` installs the Solid transform for every source file,
including `.ts`, so render tests exercised the intended reactivity. The bug only appears under the
host's real plugin loader. The new extension guard closes that gap; the report records the host
version so a future upgrade can re-check it.

## What is not verified live

These paths are covered hermetically but were not exercised against the real host during this run:

- Issue primary click: the repository has no open issues. The server-side issue launch path,
  `issueOrPullRequest` handling, and worktree branch setup are unit-tested.
- Rate-limit and stale-cache states: covered by service/TUI tests and the cache tests. The rate
  limit of the live token was not exhausted.
- OSC 8 behavior in a real terminal: only the `↗` glyph is rendered as a link, and the row-body
  click in read-only mode is a no-op under `osc8`. tmux capture could not confirm the terminal-level
  open.
- The actual browser window: the opener was verified with an injected logging script, not a visible
  browser.
- Monorepo subpath selection, remote server deployment, macOS, and Windows.
- Loading the published package target (the E2E used an absolute directory target).

## What could be better

These are not v0.1.0 blockers:

1. **Manual refresh failures are silent when data is already shown.** The refresh glyph returns to
   idle and the stale rows stay; `requestError` is only rendered when there is no summary. A failed
   manual refresh should toast or show a status line.
2. **Transient location can swallow the mount-time refresh.** When a TUI is opened directly into a
   worktree session, the sidebar can mount at the project location first. The location briefly reads
   as missing while the route settles, and one summary request is aborted (`499`). The worktree
   location then loads normally; the request is unnecessary, and the state should key refresh off a
   single captured location.
3. **OSC 8 read-only row clicks are inert.** Only the `↗` glyph carries the `<a href>`. With
   `openLinks: "auto"` over SSH, or an explicit `osc8`, a primary click on the row body returns
   success without spawning anything and without feedback. Either wrap the row title in the same
   link or show a toast explaining that the glyph is the link.
4. **Glyph hit targets are one cell.** The refresh control only reacted on column 197; the adjacent
   columns did nothing. Pad the hit area so the affordance matches its target.
5. **Branch marker does not appear for launched PR sessions.** A launched session checks out a
   synthetic local branch (`pr-4-2`), which GitHub does not have, so the branch-PR marker never
   matches. The linked marker still identifies the row. Mapping session metadata to the branch
   marker would fix this.
6. **Narrow sidebar truncation.** At the host's fixed sidebar width, titles and the second detail
   line truncate aggressively. The deferred `session.panel` is the right place for full detail.
7. **Live coverage for issues, rate limit, and stale cache.** The auth, unavailable, and browser
   paths are now verified by hand. Add the rest to the opt-in smoke or a scripted tmux E2E so the
   next host upgrade does not rely on manual clicking.
8. **Dependency queue.** #1 (`actions/checkout` 7) and #4 (`@types/node` 26) are routine but should
   land after the release tag; #3 (TypeScript 7) is a major upgrade and needs its own migration; #2
   (`solid-js` 1.9.17) should be checked against the host's Solid version before merging.
9. **Publish readiness.** The package is no longer private, the README has registry install
   instructions, and `.github/workflows/publish.yml` publishes a tagged commit with provenance. The
   release workflow builds `dist/`, rejects a source-only TUI entrypoint, and retries npm's duplicate
   Rekor-entry error. It still uses the `NPM_TOKEN` secret because npm only allows trusted-publisher
   configuration from an interactive 2FA session in the npm web UI. Once configured there, delete the
   secret; the workflow then publishes through GitHub OIDC without changes.

## Releasing

1. Set `"version"` in `package.json`, move the changelog entries under a matching heading, and merge
   the release PR to `main`.
2. Verify the package build locally, including the compiled TUI entrypoint:

   ```sh
   bun run check
   bun run pack:check
   ```

3. Tag the merged commit and push the tag:

   ```sh
   git switch main && git pull --ff-only
   git tag -a v0.1.2 -m "v0.1.2"
   git push origin v0.1.2
   ```

4. The `publish` workflow runs the full check and pack check, publishes with provenance, waits for the
   version to appear on the registry, and creates the GitHub release. It uses the `NPM_TOKEN` secret
   while present; without it, npm publishes through the workflow's GitHub OIDC identity.
5. For a missed or failed tag run, dispatch the workflow with the existing tag as the input. A
   version that is already on the registry cannot be published again; release a new version instead.
   If npm reports `TLOG_CREATE_ENTRY_ERROR`, the workflow retries with a fresh process and checks the
   registry first, because Rekor already committed the entry.

To switch to trusted publishing:

1. Open <https://www.npmjs.com/package/opencode-nexusnv-github-sidebar/access> in an authenticated
   browser and add a GitHub Actions trusted publisher for `nexusnv/opencode-nexusnv-github-sidebar`
   and `.github/workflows/publish.yml`, with publish permission. npm requires an interactive 2FA
   session for this account change; the CI token cannot perform it.
2. Delete the `NPM_TOKEN` repository secret. The next tag run uses OIDC and emits no token warning.

Provenance is generated through GitHub OIDC either way.

The registry can take up to a minute to expose a new package version. The workflow retries
verification for two minutes; if it still fails after a successful publish, create the GitHub release
for the tag manually instead of republishing.
